## 문제 2. 오차와 피드백 해석 

실행 A의 측정값을 이용하여 초기, 중간, 후반 시점의 오차를 확인하였다. 
오차는 다음과 같이 계산한다. 
```text
 error = target_deg - position_deg 
``` 

| 구간 | 시간 (s) | 목표각 (°) | 현재각 (°) | 계산한 오차 (°) |
|---|---:|---:|---:|---:|
| 초기 | 2.000 | 30.000 | 0.000 | 30.000 |
| 중간 | 2.801 | 30.000 | 12.920 | 17.080 |
| 후반 | 4.501 | 30.000 | 29.795 | 0.205 |

실제 로그의 `error_deg` 값과 직접 계산한 값이 일치하는 것을 확인하였다.

목표 위치에 가까워질수록 오차가 감소하였고, 이에 따라 계산된 P 제어 출력 p_deg_s도 함께 감소하였다. 다만 t=4.501 s에서는 p_deg_s=0.615°/s가 남아 있었지만, 최종 제어 출력 u_deg_s는 0.000°/s가 되어 정지 상태에 들어간 것을 확인하였다.

P 제어에서는 오차에 비례하여 P 제어 출력이 계산된다.

```text
  P 출력 = Kp × error 
``` 

예를 들어 `t=2.000 s`에서 오차는 `30°`이고 `Kp=3`이므로,

```text 
P 출력 = 3 × 30 = 90 °/s 
``` 
가 되며 실제 로그의 `p_deg_s:90.000`과 일치한다.

반대로 목표각이 `+30°`인데 현재각이 `+35°`라면, 

```text
 error = 30 - 35 = -5°
``` 
가 된다. 

오차가 음수가 되므로 P 출력도 음수 방향으로 발생하며, 모터를 목표 위치인 30° 방향으로 되돌리려는 제어가 이루어진다. 
현재 위치는 OpenCR이 Dynamixel에서 읽은 현재 위치값을 각도 단위의 position_deg로 사용하고, 이 값을 목표각과 비교하여 오차를 계산하는 데 사용한다.

## 문제 3. P 게인 변경에 따른 응답 비교

문제 1에서 사용한 실행 A와 동일한 목표각과 속도 제한 조건을 유지한 상태에서, `Kp` 값만 변경하여 실행 B를 수행하였다.

### 실행 조건

| 항목 | 실행 A | 실행 B |
|---|---:|---:|
| Kp | 3.0 | 0.5 |
| Ki | 0.0 | 0.0 |
| Kd | 0.0 | 0.0 |
| 속도 제한 | 20 °/s | 20 °/s |
| 상대 목표각 | +30 ° | +30 ° |

실행 A 설정:

```text
s 3 20 30
```

실행 B 설정:

```text
s 0.5 20 30
```

실행 A에서는 다음과 같이 설정된 것을 확인하였다.

```text
P SET Kp=3.0000, Ki=0.0000, Kd=0.0000, speed_limit_deg_s=20.000, angle_deg=30.000
```

실행 B에서는 다음과 같이 설정된 것을 확인하였다.

```text
P SET Kp=0.5000, Ki=0.0000, Kd=0.0000, speed_limit_deg_s=20.000, angle_deg=30.000
```

두 실행 모두 목표각이 `t=2.000 s` 부근에서 `30°`로 변경되므로, 목표 변경 이후 같은 경과 시간의 값을 비교하였다.

| 시간 `t_s` (s) | 실행 A 현재각 (Kp=3.0) | 실행 B 현재각 (Kp=0.5) | 실행 A 오차 | 실행 B 오차 |
|---:|---:|---:|---:|---:|
| 2.000 | 0.000° | 0.000° | 30.000° | 30.000° |
| 약 2.5 | 7.119° | 5.361° | 22.881° | 24.639° |
| 약 3.0 | 16.611° | 10.898° | 13.389° | 19.102° |
| 약 3.5 | 25.840° | 15.205° | 4.160° | 14.795° |
| 약 4.0 | 29.180° | 18.369° | 0.820° | 11.631° |

목표가 처음 `30°`로 변경된 시점에서 두 실행 모두 오차는 `30°`였지만, 계산된 P 제어 출력에는 큰 차이가 있었다.

```text
실행 A
Kp = 3.0
error = 30°
p_deg_s = 90.000°/s
u_deg_s = 19.236°/s

실행 B
Kp = 0.5
error = 30°
p_deg_s = 15.000°/s
u_deg_s = 15.114°/s
```

P 제어 출력은 다음과 같이 계산되므로,

```text
P 출력 = Kp × error
```

같은 오차에서도 `Kp`가 큰 실행 A의 P 출력이 실행 B보다 크게 계산된다.

실행 A에서는 계산된 P 출력이 속도 제한보다 크게 나타나 초기에는 최종 제어 출력 `u_deg_s`가 약 `19.236°/s`로 제한된 상태로 움직였다.

이후 목표에 가까워지면서 오차와 P 출력이 감소하였고, 약 `4.5 s`에는 현재각이 `29.795°`까지 도달하였다.

반면 실행 B에서는 동일한 목표각과 속도 제한을 사용하였지만 `Kp=0.5`로 설정되어 P 출력이 상대적으로 작았다.

따라서 같은 경과 시간에서 실행 A보다 현재각이 작고 오차가 더 크게 남아 있었으며, 목표 위치까지 접근하는 속도가 더 느린 것을 확인하였다.

두 실행 모두 기록된 범위에서는 목표각 `30°`를 초과하지 않았으므로 뚜렷한 오버슈트는 관찰되지 않았다.

이번에 변경한 `Kp`는 OpenCR에서 수행되는 위치 P 제어의 게인이며, Dynamixel 내부에 설정된 PID 게인을 변경한 것이 아니다.

- I항은 오차가 오랜 시간 남아 있을 경우 오차를 누적하여 정상상태 오차를 줄이는 역할을 한다.
- D항은 오차가 얼마나 빠르게 변하는지를 이용하여 급격한 움직임이나 오버슈트를 억제하는 역할을 한다.

따라서 이번 실험에서는 `Ki=0`, `Kd=0`인 P 제어 상태에서 `Kp` 값만 변경하여 응답 속도의 차이를 확인하였다.

실행 기록은 다음 파일에 저장하였다.

```text
results/실행A.log
results/실행B.log
```

## 문제 4. 제어와 통신의 역할 해석

문제 4는 실제 추가 실험 결과가 아니라 과제에서 제공된 가상 기록을 기반으로 제어와 통신 구조를 해석하였다.

과제에서 제시된 조건은 다음과 같다.

| 항목 | 조건 |
|---|---|
| OpenCR 제어 계산 주기 | 10 ms |
| 상태 발행 주기 | 100 ms |
| 목표 입력 | PC가 `/motor/target`에 30.0° 발행 |
| 상태 반환 | `/motor/state`를 통해 현재 위치값 반환 |

전체 통신 및 제어 흐름은 다음과 같이 정리할 수 있다.

```text
PC ROS2 Node
   |
   |  목표값 전송
   |  /motor/target
   v
micro-ROS Agent
   |
   |  ROS2 메시지 ↔ 임베디드 통신 연결
   v
OpenCR
   |
   |  목표각과 현재각 비교
   |  제어 계산 수행
   v
Dynamixel
   |
   |  실제 모터 움직임
   |
   |  현재 위치값 반환
   v
OpenCR
   |
   |  상태값 전달
   v
micro-ROS Agent
   |
   |  /motor/state
   v
PC ROS2 Node
```

각 구성 요소의 역할은 다음과 같다.

| 구성 요소 | 역할 |
|---|---|
| PC ROS2 Node | 목표값을 발행하고 모터의 현재 상태를 수신한다. |
| micro-ROS Agent | PC의 ROS2 통신과 OpenCR 측 임베디드 통신을 연결하는 중간 역할을 한다. |
| OpenCR | 전달받은 목표값과 현재 위치값을 이용해 제어 계산을 수행하고 Dynamixel에 제어 명령을 전달한다. |
| Dynamixel | OpenCR의 제어 명령에 따라 실제로 움직이며 현재 위치 정보를 OpenCR에 반환한다. |

### 제어 주기와 상태 발행 주기 비교

OpenCR에서는 제어 계산을 `10 ms`마다 수행하고, 상태는 `100 ms`마다 한 번씩 발행한다.

따라서 상태 메시지가 한 번 발행되는 동안 수행되는 제어 계산 횟수는 다음과 같다.

```text
100 ms ÷ 10 ms = 10회
```

즉 PC에서는 `100 ms`마다 상태값을 한 번 받아보지만, 그 사이 OpenCR 내부에서는 약 10번의 제어 계산이 수행된다.

따라서 PC가 모든 제어 계산을 직접 수행하는 것이 아니라, 빠른 주기의 실제 모터 제어는 OpenCR에서 수행되고 PC는 상대적으로 느린 주기로 목표값을 전달하고 상태를 확인하는 구조라고 이해할 수 있다.

### 통신 단절 시 처리 정책

PC와 OpenCR 사이의 통신이 끊겼을 경우에는 마지막으로 받은 목표 명령을 무기한 유지하기보다, 일정 시간 동안 새로운 명령이 들어오지 않으면 안전 정지 상태로 전환하는 정책이 적절하다고 판단하였다.

예를 들어 OpenCR에서 마지막 목표 명령을 받은 시각을 저장하고, 일정 시간 이상 새로운 명령이 수신되지 않을 경우 모터의 제어 출력을 0으로 만들어 정지시키도록 할 수 있다.

```text
정상 통신
새로운 목표 명령 수신
        ↓
제어 수행

통신 단절
새로운 명령 없음
        ↓
timeout 확인
        ↓
일정 시간 초과
        ↓
제어 출력 0
        ↓
모터 정지
```

이와 같은 정책이 필요한 이유는 통신이 끊긴 상황에서 오래된 목표 명령을 계속 실행하면 사용자가 더 이상 제어할 수 없는 상태에서도 모터가 계속 움직일 수 있기 때문이다.

따라서 통신 단절을 감지하면 기존 명령을 계속 유지하기보다 안전하게 정지시키는 것이 적절하다.
